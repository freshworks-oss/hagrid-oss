    Version [4.0.0] - [In Alpha Phase]

    We are releasing Hagrid 4.0.0 with alpha phase.

    Added

    Support for MultiParent Step

    We have added support for multi-parent step. It means, from 4.0.0 onwards, each step can have multiple parents. This has been done to increase step re-usability

    Consider a case where you have the following use case You have 5 steps in your connector from where you fetches the data and you would like to ingest all this data into Kafka as separate Step

    Support for Cycles in DAG

    We have added the support for Cycles in Hagrid DAG. Now onwards, Hagrid allow the cases where DAG can form the cycle. Most of these use cases are recursive use cases like

    1. Traversing drives and folders recursively

    2. Traversing JSON recursively

    3. Traversing web page recursively

    Consider the following DAG where there is Event Step which process events and its subsequent steps perform transformation, restructure and Tag the events so that it can be fed to Kafka.

    With Hagrid 4.0.0, developer can develop DAG which can have any number of cycles.

    Add BaggageMap in shouldProceedWithParent step method.

    We have added support for baggageMap in shouldProceedWithParent Method so that developer can filter whether execution should continue for this baggageMap or not.

    Add Stacktrace in all Error and Warn Events

    We have added stack traces in all Error or Warn log events

    Introducing shutdown and interruptSync method

    In Hagrid 3.x method, we introduce method shutdown which can be used to shutdown Hagrid from anywhere. This method used to have waitInSeconds time as parameter. We got feedback from developers that it is challenging to understand what should be the value of waitInSeconds time to have clean shutdown due to which Hagrid sometime shows un predictable behaviour

    Hence, we have made following changes in Hagrid 4.0.0 to more stream line APIs

    Interrupt Sync instead of Shutdown from Step Methods

    If you want to shutdown Hagrid sync from anywhere in traverser steps, then use newly introduce method interruptSync

    Shutdown Sync in Finally

    Use method shutdown of Hagrid syncService when you want to finally shut it down. Like from finally block of Java.

    Modified

    H2 will work on TCP mode instead of File embedded mode

    In Hagrid 3.x version, we introduce H2 database which was operating in file embedded mode. During the course of testing and discussion with other engineers, we found that H2 embedded mode show unpredictable behaviour when case of shutdown occurs.

    Hence, from hagrid 4.0.0, we will run H2 in TCP mode.

    There are two cases for this.

    Usecase 1

    If developer run their own H2 database on some POD or server, then Hagrid can use that H2 using below configuration

    Here is what changes need to be done in hagrid.yml

    infra_type: "h2"
h2_data_path: "/Users/aaggarwal/Documents/hagrid-releases/data/hagrid-3.7.0/hagrid-db-file"
h2_host_address: "x.y.z.m:9092"
h2_database_type: "tcp"

    Usecase 2 If developer do not run any H2 database server then Hagrid can run its local H2 server using below configuration. Just do not provide h2_host_address

    infra_type: "h2"
h2_data_path: "/Users/aaggarwal/Documents/hagrid-releases/data/hagrid-3.7.0/hagrid-db-file"
h2_database_type: "tcp"

    Restructuring in SyncStatus Service

    We have modified the sync status conditions in SyncStatusService to make it more consistent. Earlier, if any of the traverser or processed failed while other is still running, calling syncStatusService.getSyncStatus() used to return "-1".

    Now, Hagrid will return "0" because otherservice is still running. Hagrid will return -1 only when both traverser and processor has failed

    Restructuring of return types in Steps

    Simplify steps method return types for better coding standards Earlier, Step methods used to return Optional<HttpRequestResponse> or Optional<Boolean>.

    From version 4.0.0 all method will return primitive objects or without Optional. Hence instead of Optional<Boolean> step, method will return boolean, instead of Optional<HttpRequestResponse> method will return just HttpRequestResponse

    Extend HttpAbstractStep or NonHttpAbstractStep class

    From now onwards, developer need to extend either HttpAbstractStep or NonHttpAbstractStep class based on the type of step needs to be created.

    So for Http Based step, extend HttpAbstractStep and for non http based step, extend NonHttpAbstractStep
