# Version [3.0.0] - [1st April 2024]

Changes lead to Performance Improvements


## Fixed

### Parallelization at DAG Nodes Level
Suppose we have to create a DAG like

![img_1.png](../custom_theme/assets/images/img_1.png)


**Working in Hagrid 2.0.0**

1. When Hagrid will start processing above DAG then it will fetch all FbUsers .
2. Once all FbUsers are fetched then it will either fetch FbPost or FbCommunities
3. Suppose, it moves to FbPosts then it will fetch all FbPosts for all FbUsers
4. Once all FbPosts have been fetched then only it will start fetching FbComments


So basically, in hagrid 2.0.0, only one dag node will be processed at a time. All its child nodes have to wait until all parents data is arrived.


**Working in Hagrid 3.0.0**

Working on Hagrid 3.0.0 is completely different. It process like this

1. All nodes i.e. FbUsers , FbPosts , FbComments , FbCommunities will start processing.
2. Initially, FbPosts does not have any FbUsers to process then it will WAIT for atleast one FbUser bean to come.
3. Similarly, FbComments will wait for FbPosts and FbCommunities will wait for FbUsers
4. As soon as FbUser data will come, FbPost will process it immediately.
5. Similarly, as soon as FbPost will come, FbComment will trigger and will fetch comment for that post and for that user.


Hence, in hagrid 3.0.0, all nodes are processing in parallel.


All these is internal to Hagrid, it does not affect anything related to developer connector development process


### Parallelisation of Dag Traversal Service And ProcessorService


As a revision, Hagrid is consist of mainly two services

1. DagTraversalService - It is the service which traverse the Dag described above.
2. ProcessorService - Once DagTraversalService fetches the data ( from API ), this service is responsible to convert it to assets . These assets are consumed by developer using ConsumerService




**Working in Hagrid 2.0.0**

In hagrid 2.0.0, DagTraversalService and ProcessorService were sequential. Means, once whole DAG is traversed then only, processorService will convert beans into assets. Which leads to huge delay

```java

Class SyncService{

    public SyncContainerService startSync(some params here){


        dagTraversalService.traverse(rootNode, some_other_params)
        processorServuce.process()

    }

}

```


**Working in Hagrid 3.0.0**

In hagrid 3.0.0, DagTraversalService and ProcessorService run parallel. It means that as soon as any of the data is fetched by DagTraversalService, it will be immediately converted to Asset by processorService.


```java
Class SyncService{

    public SyncContainerService startSync(some params here){



        new Thread( () ->{
                dagTraversalService.traverse(rootNode, some_other_params);
            }).start();

        new Thread ( () ->{
            processorServuce.process();
            
            }).start()
        
    }

}
```





### Performance Improvement in FreshIndex


When ProcessorService converts beans into assets it needs a library freshIndex . It needs to index each asset generated into freshIndex so that developer can use consumerService with filter condition to get assets of particular type.


FreshIndex is the library developed by us, which provides features like filtering assets by consumerService.
For example - when a developer does consumerService.getAssetByAssetType(FbPost.class, some-filter-condition-here) then consumerService internally uses freshindex to get assets of type FbPost.class.



**Working in Hagrid 2.0.0**

In Hagrid 2.0.0, when ProcessorService index assets into freshindex , freshIndex does something like
list.contains(assetId)



list = [1,2,3,4...............1M]


Here when for every asset generated, we are matching if Id already contains, this leads to BigO(n2) complexity. Hence processorService was generating lots of beans into assets initially but slow down as soon as this list in freshIndex increases.


**Working in Hagrid 3.0.0**

In Hagrid 3.0.0, I have made changes in freshIndex to use treeMap which is the implementation of RedBlack tree. and search complexity is around BigO(logn) even for Billions of keys i..e billions of assets also.

treeMap.contains("1")  --> BigO(logN)


It leads to huge performance improvement in processorService.

All these is internal to Hagrid, it does not affect anything related to developer connector development process




### Addition of isValidResponse Method



**Working in Hagrid 2.0.0**

In Hagrid 2.0.0, hagrid does not have isValidResponse method. Whenever third-party response has status 200, hagrid assumed it to be validResponse.
However, we have encountered use cases, where in developers are saying, server respond back with 200OK but they want to decide based responseBody if it is really valid response or invalid response.

Hagrid 2.0.0, could not tackle this feature.



**Working in Hagrid 3.0.0**


In Hagrid 3.0.0, we have introduced a new method called isValidResponse . In this method developer can decide himself, whether it is valid response or not like below

**use case 1**

```java
@Override
public Boolean isValidResponse(HttpRequestResponse currentRequest, JsonNode... parentJsonObject) throws StepFailedException {

        if(currentRequest.getResponse().getCode() == 200){
            return true;
        }
        else{
            return false;
        }
    }
    
```

**use case 2**


```java

@Override
public Boolean isValidResponse(HttpRequestResponse currentRequest, JsonNode... parentJsonObject) throws StepFailedException {

        analyticsService.infoEvent("METHOD_CALLED", "name", "isValidResponse");
        if(currentRequest.getResponse().getBody().contains("error){
            return false;
        }
        else{
            return true;
        }
    }

    
```


### Addition of ParentJsonObject in all step methods

Earlier, in some methods, hagrid was not sending parentJsonObject which is required for various use cases like

1. Creating new url from parent data
2. Parsing data based on parent data



**Working in Hagrid 2.0.0**

In Hagrid 2.0.0, some methods like parseSyncResponse does not have parentJsonObject which was needed by the developer to parse the response that they have got from third-party.


```java

@Override
public StepDataBeanMapping parseSyncResponse(JsonNode jsonNode) {

}

```

**Working in Hagrid 3.0.0**

In Hagrid 3.0.0, hagrid passes parentJsonObject in almost all step objects so that hagrid can support various uses cases that come across.



```java
@Override
public StepDataBeanMapping parseSyncResponse(HttpRequestResponse httpRequestResponse, JsonNode... parentJsonObject) {
}
```

This will impact the developer who is migrating from Hagrid 2.0.0 to Hagrid 3.0.0


### Making Steps Spring Managed [ IMP ]


In Hagrid 2.0.0, there were some caveats with steps like below

1. Hagrid 2.0.0 steps were singleton
2. Constructor of Steps were hijacked by Hagrid


Lets understand, what does it mean by step were singleton . Suppose we have above Dag that we created.


**Working in Hagrid 2.0.0**

In hagrid 2.0.0, Hagrid will create just 1 Object of FbPost step and same single object will be used to process all parent items i..e Fbuser .
So essentially, you can think like this, there are multiple threads which are processing different Fbuser items using same FbPosts step instance.

So if it is so, then you can use any instance variable with in step because it will be lead to race condition and concurrency problems.


![img_1.png](../custom_theme/assets/images/img_1.png)


During the course of interactions with other developers, we found that developers tends to use instance variables within steps due to various reasons. Like - they want to have a maxRetries variable , where they will try max 3 times to fetch posts for a user and then move on to another user.

Secondly, with hagrid 2.0.0 steps, as a developer, you want to inject your services into steps so that you can encrich, track or modify some data.
It was not possible as Hagrid was inject a defined constructor which is used by Hagrid and developer can not inject any other service in it. Check below


```java

public FbUser(InfraDbList list, InfraDbKeyValue abstractKeyValue) {
super(list, abstractKeyValue);
}

```


**Working in Hagrid 3.0.0**


With Hagrid 3.0.0, now steps are like Spring boot Beans . Hagrid does not inject its own container rather it relies on Spring boot to provide the object of the hagrid step.

So with Hagrid 3.0.0, in your step, you can inject your business services and use them at various stepMethods like below



```java
@Slf4j
@FreshHierarchy(parentClass = ParentStep.class, rateLimit = 800, duration = 1)
@Component
@Scope("prototype")
public class FbUser extends AbstractStep {

    int numberOfUsersEachPage = 1;
    int numberOfPagination  = 10;
    long waitBetweenPaginationInMs = 0;

    int count = 0;
    BusinessService businessService;
    RedisService redisService;    

    @Autowired
    public FbUser(BusinessService businessService, RedisService redisService) {

        this.businessService = businessService;
        this.redisService = redisService;
        
    }
}

```


### Removal of GetData and SaveData From Steps


getData and saveData were the methods that were available in steps in Hagrid 2.0.0 to save any key, value and get value from key.
These method were saving data either in inmemory or persistent based on the infra chosen by developer in hagrid.yml



**Working in Hagrid 2.0.0**

In Hagrid 2.0.0, we as a developer can use GetData and SaveData APIs to save data and get data


@Override
public void setup(ImmutableMap<String, String> baggageMap, JsonNode... parentJsonObject) throws StepFailedException {
saveData("key", "someKey")
}




**Working in Hagrid 3.0.0**

In Hagrid 3.0.0, we have removed getData and saveData method because there were the requirements to make saveData and getData more intelligent like providing key expiry time when saving the data. More like Googles guava cache features.

So rather than modifying the saveData  and getData  and when we have made hagrid steps spring managed , developer of the connector can inject any service to save and get data.

for example


```java

@Slf4j
@FreshHierarchy(parentClass = ParentStep.class, rateLimit = 800, duration = 1)
@Component
@Scope("prototype")
public class FbUser extends AbstractStep {

    int numberOfUsersEachPage = 1;
    int numberOfPagination  = 10;
    long waitBetweenPaginationInMs = 0;

    int count = 0;
    BusinessService businessService;
    RedisService redisService;    
    Cache guavaCache;


    @Autowired
    public FbUser(BusinessService businessService,  Cache guavaCache) {

        this.businessService = businessService;
        this.redisService = redisService;
        this.guavaCache = guavaCache;
        
    }


    @Override
    public void setup(ImmutableMap<String, String> baggageMap, JsonNode... parentJsonObject) throws StepFailedException {
        
        this.guavaCache.set("key", "value")
    }
}

```


### Modifying ParseSyncResponse Parameters


ParseSyncResponse is the step method which is response to extract the only relevant data that developer wants to be rendered into beans.


**Working in Hagrid 2.0.0**

In hagrid 2.0.0, Hagrid by default, use to extract the http response body, convert it to the JsonNode and pass it to the step method parseSyncResponse .
Now develop needs return only the relevant data which can be deserialized into beans. Like below

```java

    @Override
    public StepDataBeanMapping parseSyncResponse(JsonNode jsonNode) {

        return jsonNode.get("data").get("users");
    }
    
```


With this contract of parseSyncResponse, we discovered two problems

1. It is not necessary that data is always present in body of the http response. In Some cases, relevant data is present in headers and body is empty.
2. With above contract, Hagrid will always, deserialize jsonNode data into its corresponding beans with same name. Again, there comes the case, when develop want to render it into different kind of beans based on the response.
    1. Case 1 : Suppose if response contains {“users”: “userList”} then convert it into user bean
    2. Case 2 : Suppose if response contains {“users” : “no data”} then convert it into error bean
3. This use case will come mostly in orchestrator kind of connectors where there are expected multiple kind of response for single API and developer want to process each kind of response.
4. Execution will reach to parseSyncResponse, only when you have return true for isValidResponse




**Working in Hagrid 3.0.0**


With Hagrid 3.0.0, we have address both of these problems with passing instance of HttpRequestResponse in parseSyncMethod so that developer can extract the data either from responseBody or responseHeaders .
Along with this he can render this response into any bean of his choice by making the object of StepDataBeanMapping like below


```java

@Override
public StepDataBeanMapping parseSyncResponse(HttpRequestResponse httpRequestResponse, JsonNode... parentJsonObject) {
analyticsService.infoEvent("METHOD_CALLED", "name", "parseSyncResponse");
analyticsService.infoEvent("THIRD_PARTY_API_RESPONSE");
try{
ObjectMapper objectMapper = new ObjectMapper();

            StepDataBeanMapping stepDataBeanMapping = new StepDataBeanMapping();
            String response = httpRequestResponse.getResponse().getBody();
            String errorCode = httpRequestResponse.getHeaders().get("errorCode");

            if(!Strings.isEmptyorNull(response)){
                
                JsonNode jsonNode = objectMapper.readTree(response);
                stepDataBeanMapping.setParseSyncedResponseData(jsonNode.get("data").get("users"));
                stepDataBeanMapping.setBeanClass(com.freshworks.hagrid.internal.beans.FbUser.class);
                return stepDataBeanMapping;
            }
            else{

                ObjectNode o = mapper.createObjectNode();
                o.put("errorCode", errorCode);
                stepDataBeanMapping.setParseSyncedResponseData(o);
                stepDataBeanMapping.setBeanClass(com.freshworks.hagrid.internal.beans.GeneralException.class);
                return stepDataBeanMapping;
            }

        }
        catch (Exception e){
            e.printStackTrace();
            return null;
        }
    }
    
```
